## 1. タスクごとの「変更するファイル・方針」(承認待ち)

### P0-1 データ消失の守り(4-1)

- 端末側は、すでに次の守りがあります: 空の保存を書かない(pushEmptyGuard・1102c)、減る保存を書かない(pushShrinkGuard・trial545)、読み込みに失敗したら BLANK にしない(supabaseLoadStateForStore は必ず throw)、眠っていた端末はまず取り込む(_pullIfStale)、読み込みが終わるまで保存を封鎖(dataLoadedForStoreRef)。
  - 追加: 封鎖中に保存を押したときの説明(「読み込みが終わっていないため保存できません。しばらく待つか再読み込み」)。ファイル: src/App.jsx(保存ボタン)。
- サーバー側(DDL・**本部承認が必要**): app_state の BEFORE UPDATE トリガーで「急に減る保存」を断る。
  - 提案のしきい値: `patients` が前回比 **30%以上 かつ 5人以上 減る** → 拒否。`ticketRecords` `dailyLogs` `transportPlans` `fitnessRecords` `monitoringRecords` は **50%以上 かつ 100件以上 減る** → 拒否。key が `diag_%` の行と、前回が空(新規店舗)の場合は対象外。
  - 断られた端末は 'blocked-shrink' と同じ扱い(再送しない・画面で知らせる)。
  - ファイル: docs/sql/20261121_app_state_shrink_guard.sql(移行SQL・本部が実行)、src/lib/supabase.js(サーバー拒否のエラー文の分岐)、api/state-cas.js(409 の中身をそのまま返す)。
- スナップショットから戻す手順: 復旧手順書(R-xx)に既にある手順を今の表(app_state_snapshots・app_state_daily)の名前で読み直し、追記。ファイル: docs/incident-recovery-runbook.md・api/runbook.js。

### P0-2 ログインはサーバー経由だけ(4-2)

- 方針: ブラウザから `from('staff')` を触る予備経路を **全部削除**。サーバー不達のときは「通信できません。しばらくしてからやり直してください」のエラーにする。
- ファイル: src/lib/supabase.js(supabaseStaffLogin のフォールバック、supabaseStaffChangePassword のフォールバック、店舗削除時の staff 削除、職員の追加 insert と一覧 select)。
- サーバーの鍵: api/staff-auth.js は Vercel の環境変数 SUPABASE_SERVICE_ROLE_KEY(サーバーだけ)を使っています。クライアントの環境変数(VITE_)には入っていません(確認済み)。
- `GRANT SELECT ON public.staff TO anon;` は **実行しません**。RLS も切りません。

### P0-3 古いアプリの排除(4-3)

1. 保存に端末の版を付け、サーバーで最低版未満の保存を断る。
   - 端末: /api/state-cas に `x-tsu-ver: <ビルド版>` を付ける(src/lib/supabase.js)。
   - サーバー: 環境変数 `TSUMUGI_MIN_VER`(または app_secrets の予約キー)より古い版は 409 で断る(api/state-cas.js)。断られた端末は「古い版のため保存できません。更新してください」の帯+更新ボタン(src/App.jsx)。
   - 最低版は本部が管理局で設定(初期値は 11/21 の安定版)。
2. `/reset` ページ: public/reset.html と vercel.json のヘッダ `Clear-Site-Data: "cache"`(**"storage" と "*" は使わない**=端末の下書き・端末名・ログインを消さない)。ページ側で Service Worker の解除と Cache Storage の削除を行い、index.html を取り直してトップへ戻す。
3. 版の確認を visibilitychange(画面に戻ったとき)でも行う(今はログイン画面と focus のみ)。src/App.jsx。

### P1-4 負荷を減らす(4-4)

- ポーリング: **4秒 → 20秒**。画面が隠れている間は止め、戻った瞬間に 1 回取り込む(今もある onWakePull)。Realtime 購読は継続。ファイル: src/App.jsx(checkAndPull の setInterval)。
  - 複数端末の確認(開発規律): 他端末の保存は Realtime で 1〜2 秒、Realtime 不通でも最長 20 秒で反映。保存の前の「まず取り込む」(60 秒以上空いたら)があるので巻き戻りは増えない。店舗切替・スリープ復帰は今の checkAndPull の流れのまま。
- 診断行: **60秒 → 5分**、ログは直近 20 件、変化が無ければ書かない(端末名・版・証の生存更新は 15 分に 1 回)。ファイル: src/App.jsx(送信間隔)・src/lib/supabase.js(supabaseUploadSyncDiag)。管理局「端末の更新状況」の「最後に見た時刻」の粒度が 15 分になります。
- スナップショットの保持(本部 SQL): 48 時間は全部、以後 1 日 1 件、30 日超は削除。実行前に件数を確認する SQL を先頭に付けます。pg_cron のジョブは触りません。ファイル: docs/sql/20261121_snapshot_retention.sql。
- pg_stat_statements: 本部が Supabase ダッシュボード(Database → Extensions)で有効化。読むだけ。
- コンピュート: 上の配信後 1 週間の CPU/メモリを見て、まだ 70% を超えるなら Small へ(本部の判断・月 +$10〜15)。

### P1-5 店舗データの分割(4-5)

- store_records テーブル(存在・RLS ポリシー 0・データ 0)に、diaryLogs(日誌)・transportPlans(送迎表)・faxDataStore(休み連絡の控え)・familyPersonalAnnouncements・auditLog を移す。
- 手順: C-1 二重書き(app_state と store_records の両方に書く) → C-2 1 週間の検証(件数一致を管理局で表示) → C-3 読む側を store_records に切替 → C-4 app_state から消す(消す前に AWS 控えと app_state_daily を確認)。
- これは別の設計書を出してから着手します(11/21 の安定版移行とは切り離す)。保持期間は 2〜5 年(移した記録は消さない)。

### P1-6 セキュリティ(4-6)

- パスワード: 端末で SHA-256 にしてから POST の中身で送り、サーバーで照合しています。URL には入りません。報告書の「URL に SHA-256」は旧経路(PostgREST のフィルタ)で、P0-2 の削除で無くなります。
- 次の段階: サーバー側を bcrypt(または argon2)にし、ログイン成功のたびに再ハッシュして段階的に移す。ファイル: api/staff-auth.js・api/_hash.js(新)。全員に「パスワードを変えてください」のお願いは移行後に。
- anon の app_state GET/PATCH: 段階 2 以降は職員の証(sb_token)で RLS。anon に残っている権限は、本部が docs/sql/rls_status.json と同じ確認 SQL で見ます(用意します)。

### P2-7 運用(4-7)

- DDL は docs/sql/ の移行ファイル+台帳に記録。Supabase の SQL Editor に保存されている危険な SQL(DELETE/TRUNCATE/DROP 系)は本部が削除。DB の再起動の理由は Supabase サポートに本部から問い合わせ。

### ⑤ の原因の見立て(特定店舗の 11 日・17 日)

1. その方の休止の履歴に **終了日の無い休止** が残ったまま、状態だけ「利用中」に戻っている(支援経過表はこれを「休止中」とみなしていた → 「支援経過表では休止扱い」の説明がつく)。
2. 別の端末(取り込みが遅れて、その方をまだ休止と見ている端末)が提供記録を保存すると、その日の記録が「休止」で保存される。このとき自動処理が「編集した印(時刻)」を付けるため、先に付けた「欠席」より新しい時刻になり、欠席を上書きする。
3. 次に開いた端末では「休止の期間外に残った休止」として **自動で出席に戻し**、保存で「出席」になる。→ 欠席 → 休止 → 出席 の順に変わる。

今日の修正で 2・3 の連鎖は止まります。実際にそうだったかは、本部に読むだけの SQL(docs/sql/20261121_kesseki_check.sql)を実行していただき、その 2 日の記録の状態・保存時刻・編集時刻と、終了日の無い休止の履歴を見れば確定できます(利用者は番号だけで出ます)。
データの直し(その 2 日を欠席に戻す・休止の履歴に終了日を入れる)は、店舗の提供記録入力と利用者マスタで直せます。件数が多ければ書き戻し SQL を用意します。
