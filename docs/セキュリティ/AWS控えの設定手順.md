# つむぎ 写真とデータの控え(AWS)の設定手順

2026-11-16 社長承認(別紙2「写真の保管場所の新設」)。本部の担当者が1回だけ行う作業です。
所要時間の目安: 60〜90分(AWS の口座作りが半分)。**上から順に**進めてください。

| 用語 | 意味 |
| --- | --- |
| 本体 | 店舗の端末から保存した写真と記録。いまも Supabase にあり、ここは変えません |
| 控え | 本体が壊れた・消された・乗っ取られたときに戻すための写し。AWS(大阪)に毎晩自動で取ります |
| S3 | AWS のファイル置き場 |
| バケット | S3 の中の「1つの箱」。つむぎ専用に1つ作ります |
| IAM ユーザー | AWS の中で使う「作業用の名前と鍵」。つむぎのサーバーに渡すのは、この鍵だけです |

---

## 0. 鉄則(最初に読む)

1. **鍵(アクセスキーID・シークレットアクセスキー)は、チャット・メール・LINE に書かない。**
   写すのは「管理局の画面」だけ。紙にも残さない。もし書いてしまったら、その鍵は AWS で「無効化」して作り直す。
2. **AWS の「ルートユーザー」(口座を作ったときのメールアドレス)は、口座作りと支払い設定だけに使う。**
   ルートユーザーの鍵(アクセスキー)は作らない。
3. **Supabase の「Scheduled backups」の Restore ボタンは絶対に押さない。**(復旧手順書の鉄則と同じ)
4. 控えは「入れるだけ」の設定です。**バケットの中身を手で消さない**(30日は消せない設定にするので、消そうとしてもエラーになります。正常です)。

## 1. AWS の口座を作る(ルートユーザー)

1. https://aws.amazon.com/jp/ を開き、「無料でアカウントを作成」。
2. メールアドレス: 本部の共有アドレス(例: honbu@…)。個人のアドレスにしない(退職で開けなくなるため)。
3. アカウント名(表示名): 会社名(例: `ONEs Style`)。
4. 連絡先: **ビジネス**を選び、会社の住所・電話。
5. 支払い: **本部のクレジットカード**(11/16 決定)。
6. 本人確認: 電話(SMS)に届く番号を入れる。
7. サポートプラン: **ベーシック(無料)**。
8. できたら、ルートユーザーでいったんログインする。

### 1-1 ルートユーザーに MFA(2段階認証)を付ける ★必須

1. 右上のアカウント名 → 「セキュリティ認証情報」。
2. 「多要素認証(MFA)」→「MFA デバイスの割り当て」。
3. 「認証アプリケーション」を選び、スマートフォンの Google Authenticator か Microsoft Authenticator で QR を読み取る。
   連続する2つの番号を入れて「MFA を追加」。
4. **スマホを替えたら開けなくなる**ので、QR の画面を**閉じる前に**「シークレットキーを表示」の文字列を紙に写し、金庫(鍵のかかる場所)に入れる。

### 1-2 請求の通知(使いすぎの見張り)

1. 右上のアカウント名 → 「請求とコスト管理」→ 左の「予算(Budgets)」→「予算を作成」。
2. テンプレート「月次コスト予算」、金額 **5 USD**、通知先は本部のメールアドレス。
   (想定は10店舗で月200円程度。5ドル=約750円を超えたらメールが来ます)

---

## 2. リージョン(置き場所)を「大阪」にする

画面右上の地域名(最初は「バージニア北部」など)を押し、**「アジアパシフィック(大阪) ap-northeast-3」**を選ぶ。
以後、**S3 の作業はすべて「大阪」の表示のまま**行う(別の地域で作ると、控えが日本の外に置かれます)。

---

## 3. S3 のバケット(箱)を作る

上の検索欄に `S3` と入れて開く → 「バケットを作成」。

| 項目 | 入れる値 |
| --- | --- |
| AWS リージョン | アジアパシフィック(大阪) ap-northeast-3 (2章で選んでいれば出ています) |
| バケット名 | `tsumugi-backup-<会社略称>` 例: `tsumugi-backup-onesstyle`(英小文字・数字・ハイフンのみ。世界で1つの名前なので、使われていたら末尾に数字を足す) |
| オブジェクト所有者 | ACL 無効(推奨)のまま |
| このバケットのブロックパブリックアクセス設定 | **「パブリックアクセスをすべてブロック」にチェック(4つとも ON)** |
| バケットのバージョニング | **有効にする** |
| デフォルトの暗号化 | **Amazon S3 マネージドキー(SSE-S3)**・バケットキー 有効 |
| 詳細設定 → オブジェクトロック | **有効にする**(「バージョニングが有効になります」の確認に同意) |

「バケットを作成」を押す。

### 3-1 オブジェクトロックの既定(30日は誰も消せない)

1. 作ったバケットを開く →「プロパティ」タブ →「オブジェクトロック」→「編集」。
2. デフォルトの保持: **有効化**。
3. デフォルトの保持モード: **コンプライアンス**(ルートユーザーでも期間内は消せません)。
4. デフォルトの保持期間: **30 日**。
5. 「変更の保存」。

> これで、つむぎのサーバーが置いたファイルは、置いた日から30日間は誰にも消せません。誤操作や乗っ取りがあっても控えが残ります。
> 30日を過ぎたものも自動では消えません(消すには本部が手で操作が必要)。保存期間の決まり(2年か5年)が決まったら、別途「ライフサイクルルール」で設定します。

### 3-2 バージョニングの確認

「プロパティ」→「バケットのバージョニング」が **有効** になっていること(同じ名前で上書きしても前の版が残ります)。

---

## 4. 作業用の IAM ユーザー(入れるだけの鍵)を作る

上の検索欄に `IAM` と入れて開く。

### 4-1 ポリシー(できることの一覧)を作る

1. 左の「ポリシー」→「ポリシーを作成」→ 右上の「JSON」を押す。
2. 中身を全部消して、下をそのまま貼る。**`tsumugi-backup-onesstyle` の2か所を、3章で決めたバケット名に置き換える。**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOnlyThisBucket",
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation"],
      "Resource": "arn:aws:s3:::tsumugi-backup-onesstyle"
    },
    {
      "Sid": "PutAndGetObjectsOnly",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::tsumugi-backup-onesstyle/*"
    }
  ]
}
```

3. 「次へ」→ ポリシー名 `tsumugi-backup-put-only` → 「ポリシーの作成」。

> 消す権限(`s3:DeleteObject`)も、設定を変える権限も入っていません。この鍵が漏れても「置く・読む」しかできません。

### 4-2 ユーザーを作る

1. 左の「ユーザー」→「ユーザーの作成」。
2. ユーザー名 `tsumugi-backup`。「AWS マネジメントコンソールへのアクセスを提供する」は**チェックしない**(画面にログインする必要は無い)。
3. 「次へ」→「ポリシーを直接アタッチする」→ 検索欄に `tsumugi-backup-put-only` → チェック → 「次へ」→「ユーザーの作成」。

### 4-3 アクセスキーを作る

1. 作ったユーザー `tsumugi-backup` を開く →「セキュリティ認証情報」タブ →「アクセスキーを作成」。
2. ユースケース: **「AWS の外部で実行されるアプリケーション」**→「次へ」→ 説明タグ `tsumugi vercel` →「アクセスキーを作成」。
3. 画面に **アクセスキーID**(AKIA で始まる)と **シークレットアクセスキー** が出ます。
   **この画面を閉じると、シークレットは二度と表示されません。** 次の5章の管理局の画面を別のタブで開いて、そのまま貼り付けてください。
   (閉じてしまったら、このキーを「無効化」→「削除」して、もう一度作ればよい)

---

## 5. 管理局に4つの値を入れる

1. つむぎ(https://tsumugi.ones-style.co.jp)に本部でログイン → 管理局 → **外部サービス設定**。
2. 「**AWS S3（写真の控え）**」の欄に次の4つを入れて保存。

| 画面の項目 | 入れる値 | 保存先の名前(参考) |
| --- | --- | --- |
| アクセスキーID | 4-3 の AKIA… | `aws_access_key_id` |
| シークレットアクセスキー | 4-3 のシークレット | `aws_secret_access_key` |
| リージョン | `ap-northeast-3`(空欄でも大阪になります) | `aws_region` |
| バケット名 | 3章で作った名前 | `aws_bucket` |

3. **「接続テスト」**を押す。
   - 「バケット … に書き込めました。最後の控え: まだ実行されていません」→ 成功。4-3 のタブは閉じてよい。
   - 「アクセスキーIDまたはシークレットアクセスキーが違います」→ 貼り間違い。前後の空白が入っていないか確認。
   - 「バケット名が違います」→ 3章の名前と見比べる。
   - 「リージョンが違います」→ `ap-northeast-3` にする。バケットを大阪以外で作っていたら、3章からやり直し。
   - 「権限が足りません」→ 4-1 の JSON のバケット名が合っているか、4-2 でポリシーを付けたか確認。

> 接続テストは `health/last_test.txt` という小さな文字ファイルをバケットに置きます(これも30日は消せません。問題ありません)。

## 6. 最初の晩の確認

- 控えは **毎晩 03:30(日本時間)** に自動で動きます(Vercel の定時実行 `/api/backup-photos`・UTC 18:30)。
- 1回の実行で写すのは **150 ファイル・45秒まで**。最初は写真が多いので、数晩に分けて追いつきます(「残り」が 0 になるまで)。それ以降は毎晩「増えた分だけ」です。
- 店舗データ本体(app_state)は店舗ごとに **1日1回**、`app_state/<店舗ID>/<日付>.json.gz` として写します。

翌朝の確認(2通り、どちらでも):

1. 管理局 → 外部サービス設定 → AWS の「接続テスト」を押す → 「最後の控え: 2026-xx-xx 03:3x JST」と出れば動いています。
2. 本部の PC で(鍵を環境変数に入れてから)
   `node scripts/restore_from_s3.mjs --status`
   → `finishedAt`・`copied`(写した数)・`remaining`(残り)・`errorCount`(0 が正常)が出ます。

S3 の画面で見る場合: バケットを開くと `storage/`(写真)・`app_state/`(店舗データ)・`manifest/`(台帳)・`health/`(テスト)の4つのフォルダがあります。

すぐ動かして確かめたいとき(本部のみ): 管理局の合言葉(ADMIN_API_SECRET)を使い、
`POST /api/backup-photos` に `{ "secret": "<合言葉>", "dryRun": true }` を送ると、**何も書かずに**「写す予定の件数」だけ返ります。`dryRun` を外すと実際に写します。

## 7. 費用の目安

| 店舗数 | 月額(目安) |
| --- | --- |
| 10店 | 約200円 |
| 30店 | 約300〜400円 |
| 100店 | 約600〜1,000円 |

前提: 1店舗 写真 0.5GB+店舗データの控え30日分 0.3GB、1GB あたり月 0.025 ドル、1ドル150円。
AWS の請求は毎月、1-2 で入れたメールアドレスに来ます。**5ドルを超える通知が来たら**本部へ連絡(写真の置き方が変わった可能性)。

## 8. してはいけないこと

- **Supabase の Restore ボタンを押さない。**(本番全体が巻き戻り、全店の入力が消える)
- 鍵をチャット・メール・LINE・共有ドキュメントに書かない。管理局の画面にだけ入れる。
- ルートユーザーのアクセスキーを作らない。ルートユーザーで日常の作業をしない。
- バケットの「ブロックパブリックアクセス」を外さない。オブジェクトロックの設定を変えない。
- IAM ユーザー `tsumugi-backup` に `s3:DeleteObject` や `AdministratorAccess` を足さない。
- 大阪以外のリージョンにバケットを作らない。
- 鍵が漏れたかもしれないとき: IAM → ユーザー `tsumugi-backup` → セキュリティ認証情報 → そのキーを「無効化」→ 新しいキーを作って管理局に入れ直す(控えは次の晩から続きます)。

## 9. 控えから戻す(復旧手順の要点)

戻す作業は **本部だけ** が、復旧手順書(docs/incident-recovery-runbook.md・Web版 /api/runbook)の鉄則に従って行います。S3 から Supabase へ自動で戻す仕組みは**あえて作っていません**(間違った版で上書きしないため)。

### 9-1 取り出す(本部の PC)

1. ターミナルで鍵を環境変数に入れる(コマンドの引数には書かない)。
   ```
   export AWS_ACCESS_KEY_ID=…  AWS_SECRET_ACCESS_KEY=…  AWS_BUCKET=tsumugi-backup-xxxx
   ```
2. 何があるか見る:
   `node scripts/restore_from_s3.mjs --status`
3. 店舗の写真をまとめて取り出す(店舗データ本体に出てくる写真だけ・写真の置き場所には店舗の区別が無いため):
   `node scripts/restore_from_s3.mjs --store store_ogibashi --out ~/Desktop/tsumugi_restore`
   `--since 2026-11-01` を足すと、その日以降に写したものだけ。
4. 特定の方の写真だけ: `node scripts/restore_from_s3.mjs --download --prefix storage/pf/14/ --out ~/Desktop/tsumugi_restore`
5. 店舗データ本体のある日の控え: `node scripts/restore_from_s3.mjs --app-state store_ogibashi 2026-11-16 --out ~/Desktop/tsumugi_restore`
   → `~/Desktop/tsumugi_restore/app_state/store_ogibashi/2026-11-16.json`

取り出した先: `<out>/storage/<Storage と同じパス>`(例 `storage/pf/14/hokensho.jpg`)。

### 9-2 戻す

- 写真: Supabase ダッシュボード → Storage → `personal-files` → **同じフォルダ(例 pf/14/)に、同じファイル名で**アップロードする。利用者マスタの個人ファイルの一覧はパスで見ているので、同じパスに戻れば画面に出ます。
- 店舗データ本体: 取り出した JSON を**そのまま上書きしない**。復旧手順書の「別の場所に取り出して → 欠けている部分だけを SQL で書き戻す」方式で、必要な利用者・記録だけを戻す。
- 戻した後は、店舗の端末で「表示 → 再読込 → 個人ファイルが開く」まで確認する(新機能はテスト店舗で実機確認、の決まりと同じ)。

### 9-3 練習(12月中・本部)

本番に触らずにできる練習: `--status` → `--list --prefix storage/pf/` → 1名分を `--download` で取り出し → 画像が開くことを確認。年に1回はやる。

## 付録: 仕組みのまとめ(技術担当向け)

| 項目 | 内容 |
| --- | --- |
| 実行 | Vercel Cron `/api/backup-photos`・毎日 18:30 UTC(03:30 JST)・`CRON_SECRET` があれば照合 |
| 手動 | `POST /api/backup-photos { secret: ADMIN_API_SECRET, dryRun?, maxFiles?, budgetMs? }` |
| 状況 | `POST /api/backup-status { secret }` または本部の職員の証 `{ token }` |
| 設定 | app_secrets: `aws_access_key_id` / `aws_secret_access_key` / `aws_region` / `aws_bucket`(環境変数 `AWS_ACCESS_KEY_ID` 等があれば優先) |
| 写す元 | Supabase Storage `personal-files` の全階層(1000件ずつページ送り)・app_state の `store_*` |
| 写す先 | `storage/<同じパス>`・`app_state/<店舗ID>/<YYYY-MM-DD>.json.gz`・台帳 `manifest/latest.json`・要約 `manifest/last_run.json` |
| 増分の判定 | 台帳にある size・updated_at・eTag が同じなら写さない |
| 1回の上限 | 150 ファイル・45 秒(`vercel.json` の maxDuration 60)。残りは次の晩 |
| 署名 | AWS 署名 v4 を `api/_s3.js` で自前(依存の追加なし)。Object Lock のため PutObject に Content-MD5 を付ける |
| 消す操作 | どこにも無い(Supabase 側は読むだけ・S3 側は置くだけ) |

## 付記(2026-11-18 本部の実施記録)

- 新しい AWS の画面(ビルダー ID・「プロジェクト」方式)では、プロジェクト側の口座(Hello World)は地域がシドニー限定で、大阪にバケットを作る権限もありません。**バケットと IAM は「管理アカウント(honbu-Team Management Account)」に作りました。** 設定画面 → 管理アカウント → 「組織を一元管理する」で入れます。
- 右上に大阪が出ないときは、歯車 → 統一された設定 → ユーザー設定 → 「デフォルトのリージョン」を大阪にして「新しいデフォルトのリージョンに移動」。
- 管理局のリージョンの欄は空欄のままで大阪になります(1118c で環境変数名を TSUMUGI_AWS_REGION に変更。Vercel が AWS_REGION を自動で入れるため)。
- 11/18 接続テスト成功。Hello World / Identity Delegated Admin の口座は消さずに残す(閉鎖は控えが数日動いたあとに検討)。
- 管理局の合言葉(ADMIN_API_SECRET)は Vercel で「Secret」型のため再表示できません。忘れたら Vercel → Settings → Environment Variables で新しい値を入れて保存 → Deployments → Redeploy。

## 付記(2026-11-19) 控えに入るもの

毎晩 03:30 に、次を大阪の S3 に写します(1119a〜1119c)。順番は上から。時間切れは次の晩に続きから。

| 置き場所 | 中身 | 頻度 |
| --- | --- | --- |
| app_state/<店舗>/<日付>.json.gz | 店舗データ本体(利用者マスタ・各種設定・送迎表・計画書・日誌・連絡帳 など) | 毎晩・店舗ごと |
| ticket_records/<店舗>/<日付>.json.gz | 提供記録(表の全行) | 毎晩・店舗ごと |
| tables/<表>/<日付>.json.gz | 店舗一覧・職員・招待・ログインの記録・ご家族/ケアマネのアカウントと招待・お知らせ・元に戻す控え・同期の履歴(35日分)・店舗以外の app_state | 毎晩 |
| storage/… | 写真・PDF などのファイル(個人ファイルの添付) | 新しい/変わったものだけ |
| manifest/ | 控えの台帳と最後の実行の要約 | 毎回 |

入れないもの: app_secrets(外部サービスの鍵)。鍵の控えを控え先に置かないため。復旧のときは管理局で入れ直す。
自動テスト T-BK-01 が「API の触る表がすべて控えの対象か」を毎回確かめる(新しい表を足したら api/backup-photos.js の TABLES にも足す)。
